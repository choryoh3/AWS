# 07. 運用（作った後に、安全に長く動かす）

## 0. 運用とは何か

作って終わりではなく、次の 6 つを**繰り返す**ことです。

1. **見る**（監視）：異常に早く気づく
2. **払う**（コスト管理）：想定外の請求を防ぐ
3. **守る**（セキュリティ）：漏えい・乗っ取りを防ぐ
4. **戻す**（バックアップと復元）：事故から立ち直れるようにする
5. **直す**（更新とパッチ）：古い部品を残さない
6. **消す**（後片付け）：使わないものを残さない

この章は、その毎日・毎週・毎月の作業表と、障害が起きたときの初動をまとめたものです。

## 1. 作業表（これをそのまま使う）

### 1.1 毎週（15 分）

| 作業                         | 見る場所                                    | 問題のサイン                       |
| ---------------------------- | ------------------------------------------- | ---------------------------------- |
| 今月の費用と、利用上限の残り | Billing and Cost Management → Cost Explorer | 先週より大きく増えている           |
| 予算・利用上限の通知メール   | メールの受信箱                              | 50% / 80% の通知が届いている       |
| SES のバウンス・苦情の件数   | SES → Account dashboard、通知の SNS         | 苦情が増えている、バウンスが多い   |
| 使っていないリソースの有無   | EC2 の Instances、RDS の Databases          | 停止・使っていないものが残っている |

### 1.2 毎月（60 分）

| 作業                                                             | 理由                                       | 参照               |
| ---------------------------------------------------------------- | ------------------------------------------ | ------------------ |
| EC2 の OS を更新する（`sudo dnf update -y`）                     | セキュリティ修正を取り込む                 | 03 章              |
| RDS の自動バックアップが有効か確認する                           | 復元できない状態を防ぐ                     | 05 章 8            |
| RDS の空き容量と CPU を確認する                                  | 容量不足・負荷の異常に早く気づく           | 05 章 11           |
| S3 のパブリックアクセスのブロックを確認する                      | 誤った公開を防ぐ                           | 04 章 10           |
| SG（セキュリティグループ）に、`0.0.0.0/0` の開放が無いか確認する | 一時的な開放の消し忘れを防ぐ               | 02 章 8            |
| 復元の練習（スナップショットから別の DB を作って、消す）         | バックアップは、復元できて初めて意味がある | 05 章 11.3         |
| 不要なスナップショット・ボリューム・Elastic IP を消す            | 残っていると、料金と混乱の元になる         | 03 章 10、05 章 10 |

### 1.3 半年〜年 1 回

| 作業                                         | 理由                                   | 参照                |
| -------------------------------------------- | -------------------------------------- | ------------------- |
| SMTP 認証情報・DB のパスワードの作り直し     | 古い秘密の値の悪用を防ぐ               | 05 章 7、06 章 11.2 |
| 権限（IAM）の棚卸し（今も必要な権限か）      | 使わなくなった権限を残さない           | 下の 3.2            |
| 利用中のサービス・インスタンスタイプの見直し | 過大な構成で払い続けていないか確認する | 下の 2.3            |
| MFA の登録状態（予備があるか）               | 端末の紛失で締め出されないようにする   | 01 章 5             |

## 2. コスト管理（払いすぎないための仕組み）

### 2.1 三重の安全網

| 層  | 仕組み                      | 何をしてくれるか                                   |
| --- | --------------------------- | -------------------------------------------------- |
| 1   | AWS Budgets（予算）         | 金額が近づいたら、メールで気づかせる（止めない）   |
| 2   | 利用上限（spend limit）     | 上限に達したら、プロジェクトのリソースを**止める** |
| 3   | 毎週の Cost Explorer の確認 | 人間が、何に払っているかを理解する                 |

**なぜ三重か**: 1 つだけでは、通知を見逃すことがあり、上限だけでは、学習中に突然止まってしまうため。

### 2.2 タグで費用を分ける

- すべてのリソースに、`Project=login-app` と `Env=learning` を付ける（作成時の手順で入れている）。
- **Billing → Cost allocation tags** で、タグを有効化すると、Cost Explorer でタグごとの費用が見られる（有効化は、反映まで時間がかかることがある）。
- **なぜ**: 「どのリソースが、いくら使っているか」が一目で分かるため。

### 2.3 費用が増える典型的な原因

| 原因                                   | 対策                                                     |
| -------------------------------------- | -------------------------------------------------------- |
| NAT Gateway を作ったまま               | 学習では作らない（02 章）                                |
| EC2 を Stop せず、起動したまま         | 使わない時間は Stop（03 章 8）                           |
| RDS を停止したまま、7 日後に自動で起動 | 再開の日を決め、使わないなら削除（05 章 9）              |
| EBS・スナップショットが残っている      | 作業後に、ボリュームとスナップショットを確認（03 章 10） |
| Elastic IP を、使わずに持っている      | 使わないなら解放（03 章）                                |
| S3 の古い版が増え続ける                | ライフサイクルで古い版を削除（04 章 7）                  |
| 大きすぎるインスタンス・ストレージ     | 学習の構成（t3.micro / db.t4g.micro）から始める          |

### 2.4 「止める」と「消す」の使い分け

- **止める**：数日〜数週間後にまた使う。データを残したい。
- **消す**：もう使わない。データは、スナップショットや S3 に移してから消す。
- **迷ったら**：消す前に、スナップショットを取る。スナップショットも、不要になれば消す。

## 3. セキュリティ運用

### 3.1 秘密の値の管理

| 秘密の値                              | 置き場所                                       | 作り直す時期                                                 |
| ------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| DB のパスワード（マスター・アプリ用） | Secrets Manager                                | 年 1 回、または漏えいの疑い                                  |
| SMTP 認証情報（SES）                  | Secrets Manager、または Amplify のシークレット | 年 1 回、または漏えいの疑い                                  |
| `BETTER_AUTH_SECRET`                  | Amplify のシークレット                         | 変えると、**全ユーザーがログアウトされる**（計画して変える） |
| MFA の端末                            | 2 台以上に登録                                 | 端末を変えた時                                               |

**やってはいけないこと**

- 秘密の値を、Git・チャット・スクリーンショット・ログに出す。
- 秘密の値を、`.env` などの平文ファイルとして共有する（個人の PC だけに置く）。
- 秘密の値を、コマンドの引数に直接書く（シェルの履歴に残るため）。`read -s` などで入力する。

### 3.2 権限の考え方（最小権限）

- **人**：日常は、Builder ID（管理者の権限）でも、作業のときだけ使う。普段の作業では、読み取り専用の権限で十分な場面が多い。
- **アプリ**：必要な操作だけ（例：S3 は読み書き、SES は送信だけ、DB は自分のデータベースだけ）。
- **EC2**：`AmazonSSMManagedInstanceCore` だけ（03 章 4）。

**確認方法**: IAM → Users / Roles → 各ポリシーの「Last accessed（最後に使われた日時）」を見る。1 年使われていない権限は、外す。

### 3.3 ログ（誰が何をしたか）

- **CloudTrail**：AWS 上の操作（作成・削除・権限の変更）の記録。コンソールの **Event history** で、直近 90 日分が見られる（公式の記載として、一般的な説明です。詳細は CloudTrail のドキュメントで確認）。
- **なぜ**: 「いつ、誰が、このリソースを消したのか」を調べるため。

### 3.4 公開の確認

| 確認項目                    | 方法                                                               |
| --------------------------- | ------------------------------------------------------------------ |
| S3 が公開されていないか     | S3 → 各バケット → Permissions → Block public access が 4 つとも On |
| SG で開いているものが無いか | 02 章 8 の確認コマンド                                             |
| RDS が公開されていないか    | RDS → 各 DB → Publicly accessible が「No」                         |
| EC2 にインバウンドが無いか  | EC2 → Security → Inbound rules が空（踏み台の場合）                |

## 4. 監視（CloudWatch）

### 4.1 最低限のアラーム

| 対象 | 指標                  | 条件（例）       | 理由                                                                         |
| ---- | --------------------- | ---------------- | ---------------------------------------------------------------------------- |
| EC2  | CPUUtilization        | 80% を 15 分以上 | 暴走・攻撃の予兆                                                             |
| RDS  | FreeStorageSpace      | 2 GiB 以下       | 容量不足で DB が止まるのを防ぐ                                               |
| RDS  | CPUUtilization        | 80% を 15 分以上 | 負荷の異常                                                                   |
| RDS  | DatabaseConnections   | 想定より多い     | アプリの接続漏れ                                                             |
| 請求 | EstimatedCharges（※） | 想定額を超えたら | 予算の補助（※ 請求アラームは、米国東部リージョンで作る必要があるかは要確認） |

**作り方（コンソール）**: CloudWatch → Alarms → Create alarm → メトリクスを選ぶ → しきい値を入れる → 通知先（SNS のトピック、メールアドレス）を選ぶ。

### 4.2 通知先の作り方（SNS）

1. SNS → Topics → Create topic（例: `login-app-alerts`）。
2. Create subscription → Protocol: **Email** → 自分のアドレス。
3. 届いた確認メールのリンクを開く（開かないと通知が届かない）。

**なぜ**: アラームを作っても、通知先が無いと誰も気づかないため。

## 5. バックアップと復元

### 5.1 何を、どこで、どれだけ残すか

| 対象            | 方法                 | 保持            | 復元の方法                             |
| --------------- | -------------------- | --------------- | -------------------------------------- |
| RDS（DB）       | 自動バックアップ     | 7 日            | スナップショットから、新しい DB を作る |
| RDS（DB）       | 手動スナップショット | 消すまで        | 同上                                   |
| EC2（ディスク） | EBS スナップショット | 消すまで        | ボリュームを作り、EC2 に付け替える     |
| S3（ファイル）  | バージョニング       | 90 日（古い版） | 古い版を指定して、取り出す（04 章 5）  |

### 5.2 復元の練習（月 1 回）

1. RDS の最新の自動バックアップ（またはスナップショット）から、**別の名前**で DB を作る。
2. 接続して、テーブルとデータが読めるか確認する。
3. 確認後、練習用の DB を削除する（削除保護をオフにしてから）。

**なぜ**: 「バックアップがある」と「復元できる」は違う。練習して初めて、本当に戻せると分かる。

### 5.3 変更の前には、必ずスナップショット

- DB のスキーマ変更（マイグレーション）、大きなアップデートの前。
- 名前に、日付と変更内容を入れる（例: `login-app-db-before-migration-20261201`）。

## 6. 更新とパッチ

| 対象                           | 方法                                                   | 注意                                           |
| ------------------------------ | ------------------------------------------------------ | ---------------------------------------------- |
| EC2 の OS                      | `sudo dnf update -y`（毎月）                           | 再起動が必要な更新もある。作業時間を決めて行う |
| RDS の PostgreSQL              | メンテナンス時間に自動適用（通知が来たら確認）         | メジャー版の更新は、テスト用の DB で先に試す   |
| アプリ（Amplify）              | Git への push で自動デプロイ                           | 本番の前に、テスト環境で確かめる               |
| 依存パッケージ（Node.js など） | 定期的に更新し、`pnpm test` と `pnpm build` で確かめる | 壊れたら、直前のバージョンに戻す               |

## 7. 障害対応（初動）

### 7.1 基本の順番

1. **落ち着いて、影響を確認する**：どの機能が、どのくらいの人に影響しているか。
2. **止血する**：被害を広げないために、止める（例：課金の急増なら、リソースを Stop）。
3. **原因を調べる**：CloudWatch・CloudTrail・アプリのログを見る。
4. **直す**：元に戻す（スナップショットからの復元、前のバージョンへの切り戻し）。
5. **記録する**：何が起き、何をして、何を変えたかを残す（再発防止のため）。

### 7.2 典型的な障害と初動

| 症状                                     | 最初にやること                                                            | 次にやること                                        |
| ---------------------------------------- | ------------------------------------------------------------------------- | --------------------------------------------------- |
| 請求が急に増えた                         | Cost Explorer で、どのサービスが増えたか確認。該当リソースを Stop         | 原因（Stop 忘れ、NAT Gateway など）を消し、再発防止 |
| 秘密の値が漏えいした（疑い含む）         | 該当の秘密の値を、**すぐに作り直す**（06 章 11.2、05 章 7）               | 不正なアクセスの有無を、CloudTrail で確認           |
| ログインできない（認証コードが届かない） | SES の送信状況（Account dashboard）、サンドボックスか確認                 | 06 章 11.3 のトラブルシューティング                 |
| 苦情・バウンスが急増                     | SES の送信を一時停止（送信元の変更、または送信を止める）                  | 宛先リストを見直す。同意のない送信を止める          |
| DB に接続できない                        | RDS の状態（Available か）、SG の 5432 が踏み台から許可されているか       | 接続数（DatabaseConnections）の異常を確認           |
| DB を誤って消した                        | 自動バックアップ・最後のスナップショットから復元                          | 復元した DB に、アプリの接続先を切り替える          |
| EC2 に入れない                           | SSM の状態（Fleet Manager）、インスタンスプロファイル、インスタンスの状態 | 03 章 6 の確認順                                    |

### 7.3 やってはいけないこと（障害の時ほど）

- 原因が分からないまま、いくつものリソースを一度に消す。
- ログを消してから調べる（先に保存する）。
- SG を一時的に `0.0.0.0/0` で開けて、そのまま忘れる。

## 8. 後片付け（学習の終わり）

学習が終わったら、次の順番で消します。**依存関係のあるものを、先に消す**のがコツです。

| 順番 | 対象                                                            | 手順の章            |
| ---- | --------------------------------------------------------------- | ------------------- |
| 1    | RDS（削除保護をオフにして、最後のスナップショットを取り、削除） | 05 章 10            |
| 2    | EC2（Terminate。ボリュームが残っていないか確認）                | 03 章 10            |
| 3    | スナップショット（RDS・EBS）のうち、不要なもの                  | 05 章 10、03 章 9.3 |
| 4    | S3 のバケット（中身と、すべての版を消してから削除）             | 04 章 10            |
| 5    | Elastic IP（使っていれば解放）                                  | 03 章 10            |
| 6    | DB サブネットグループ・セキュリティグループ・VPC                | 02 章 9             |
| 7    | SES の Identity、SMTP 用の IAM ユーザー、SNS のトピック         | 06 章 12            |
| 8    | IAM のロール・インスタンスプロファイル（不要なら）              | 03 章 4             |
| 9    | Budgets・利用上限（残す。次の学習で役立つ）                     | 01 章               |

**最後の確認**

- [ ] Billing → Bills で、今月の利用額を確認した
- [ ] EC2 の Instances が、すべて Terminated か、リストに無い
- [ ] RDS の Databases が空（スナップショットは、必要なものだけ）
- [ ] S3 のバケットが、残したいもの以外に無い
- [ ] Elastic IP が無い
- [ ] SES の Identities が、残したいものだけになっている

## 9. 運用の記録（推奨）

- 変更をしたら、**日付・何を・なぜ・誰が**を 1 行で残す（例: `2026-12-01 sg-db に 5432 を追加。理由: 踏み台からの接続確認。担当: 〇〇`）。
- 記録の場所は、このリポジトリの `docs/aws/` に `CHANGELOG.md` を作って残すのがおすすめ（秘密の値は書かない）。
- **なぜ**: 半年後に「なぜこの設定なのか」を、誰でも説明できるようにするため。

## 10. 要確認

1. 請求アラーム（EstimatedCharges）の作成場所（米国東部リージョンが必要か）
2. CloudTrail の Event history の保持期間（90 日の記載は一般的な説明。公式で確認）
3. 簡易版で、CloudWatch のアラームと SNS が、無料枠の対象として使えるか
