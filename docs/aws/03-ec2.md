# 03. EC2（仮想サーバー）と SSM Session Manager

## 0. なぜ EC2 を作るか

このアプリ本体は Amplify Hosting に載せる予定です。それでも EC2 を学ぶ理由は次の 3 つです。

1. **サーバーの基本**（OS、ディスク、停止・起動、料金の仕組み）を、手で触って理解するため。
2. **DB に安全に入る踏み台**を作るため。RDS は非公開に置くので、入る道が必要。
3. サーバー型の運用（OS の更新、監視、バックアップ）を学ぶため。

## 1. 公式ドキュメント

- Amazon EC2 の基本概念: https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/concepts.html
- インスタンスの停止と起動: https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Stop_Start.html
- Session Manager: https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager.html

## 2. 基本の概念

| 用語                                       | 意味                     | 初心者へのポイント                                                                                                                     |
| ------------------------------------------ | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| **インスタンス**                           | 仮想サーバー 1 台        | 「EC2 を作る」＝「インスタンスを起動する」                                                                                             |
| **インスタンスタイプ**                     | CPU・メモリの大きさ      | 学習は `t3.micro`（x86）か `t4g.micro`（Arm 系 Graviton）。どちらも小さい                                                              |
| **AMI**                                    | OS のひな形              | 学習は **Amazon Linux 2023** を選ぶ                                                                                                    |
| **EBS**                                    | インスタンスのディスク   | **停止中もディスク料金がかかる**                                                                                                       |
| **インスタンスストア**                     | サーバーの内蔵ディスク   | **停止すると中身が消える**（公式の記載）                                                                                               |
| **パブリック IP アドレス**                 | インターネットからの住所 | **停止→起動で変わる**（公式の記載：新しいホストに載り、新しい IP が割り当てられる）。固定したいときは Elastic IP（料金の扱いは要確認） |
| **キーペア（SSH 鍵）**                     | SSH で入るための鍵       | 本ガイドでは使わない（SSM で入るため）                                                                                                 |
| **インスタンスプロファイル（IAM ロール）** | サーバーに付ける権限     | SSM を使うために必須                                                                                                                   |

## 3. なぜ SSH ではなく SSM Session Manager か

- **SSH は、ポート 22 を開ける**必要がある。世界中から攻撃を受けやすい。
- **Session Manager は、ポートを開けずに入れる。** 公式の記載では「inbound ports を開けずに、ノードを管理できる」と説明されています。
- 誰が入れるかは **IAM の権限で制御**する（鍵の配布が要らない）。
- 操作の記録を残せる（ログ設定が必要。別途設定する）。

**結論**: 本ガイドの踏み台は、**インバウンドのルールが 1 つも無い**状態で運用します（02 章の `sg-bastion`）。

## 4. 手順 A：IAM ロールを作る（EC2 に付ける権限）

**なぜ**: EC2 が「SSM の仕組みに接続してよい」と認められるための権限を、EC2 自身に持たせるため。

**手順（コンソール）**

1. **IAM → Roles → Create role**。
2. Trusted entity type: **AWS service**、Use case: **EC2**。
3. 権限ポリシーで **`AmazonSSMManagedInstanceCore`** を選ぶ。
4. ロール名: `login-app-bastion-role`。作成。

**CLI**

```bash
# 信頼ポリシー（EC2 がこのロールを使えるようにする）
cat > trust.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ec2.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
EOF

aws iam create-role --role-name login-app-bastion-role \
  --assume-role-policy-document file://trust.json

aws iam attach-role-policy --role-name login-app-bastion-role \
  --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore

# EC2 に付けるための「インスタンスプロファイル」を作り、ロールを入れる
aws iam create-instance-profile --instance-profile-name login-app-bastion-profile
aws iam add-role-to-instance-profile --instance-profile-name login-app-bastion-profile \
  --role-name login-app-bastion-role
```

> **注意**: 権限は `AmazonSSMManagedInstanceCore` だけにする。`AdministratorAccess` などの強い権限を付けない。

## 5. 手順 B：インスタンスを起動する

**手順（コンソール）**

1. **EC2 → Instances → Launch instances**。
2. 名前: `login-app-bastion`。
3. **AMI**: Amazon Linux 2023 AMI（x86 または Arm64）。
4. **インスタンスタイプ**: `t3.micro`（x86 の場合）または `t4g.micro`（Arm64 の場合）。**AMI と CPU の種類を揃える**（x86 の AMI に Arm のタイプは使えない）。
5. **キーペア**: **Proceed without a key pair（キーペアなしで続行）**。SSM で入るため不要。
6. **ネットワーク設定**
   - VPC: `login-app-vpc`
   - Subnet: **public-a**（パブリックサブネット）
   - Auto-assign public IP: **Enable**（外へ出るための IP）
   - Firewall（セキュリティグループ）: **既存の `sg-bastion`** を選ぶ（Inbound は無し）
7. **ストレージ**: 8 GiB（既定）、gp3 のまま。
8. **詳細設定** → **IAM instance profile**: `login-app-bastion-profile` を選ぶ。
9. **タグ**: `Name=login-app-bastion`、`Project=login-app`、`Env=learning`、`Owner=自分の名前`。
10. **Launch instance**。

**なぜ public-a に置くか**: SSM Agent（EC2 の中で動く管理ソフト）が、SSM の仕組みと通信するために、外への通信（アウトバウンド）が必要です。学習では NAT Gateway を作らないため、パブリックサブネットに置き、インバウンドは閉じたままにします。

> **なぜ `sg-bastion` で「インバウンドが 0」が安全か**: 外からの接続は、すべて遮断されます。それでも SSM は、EC2 から外へ向かう通信で接続を開始するため、入り口を開けずに済みます。

## 6. 手順 C：接続する（Session Manager）

**コンソールから**

1. EC2 → Instances → `login-app-bastion` を選ぶ。
2. **Connect → Session Manager → Connect**。

**CLI から**（事前に AWS CLI に **Session Manager プラグイン**のインストールが必要）

```bash
aws ssm start-session --target i-0123456789abcdef0 --region $REGION
```

- `i-...` はインスタンス ID（EC2 の画面に表示される）。
- 接続できない場合は、次の順に確認する。
  1. インスタンスの状態が **running** か
  2. IAM インスタンスプロファイルが付いているか
  3. SSM のマネージドインスタンス一覧（Fleet Manager）に表示されるまで、数分待つ
  4. 外向きの通信（アウトバウンド）が遮断されていないか

## 7. 手順 D：サーバーの初期設定（OS の更新・道具の準備）

接続した後、次のコマンドを実行します。

```bash
# OS のパッケージを最新にする（セキュリティ更新）
sudo dnf update -y

# PostgreSQL のクライアント（psql）を入れる
# 注意: 利用できるバージョン名は環境で違うため、先に検索する
sudo dnf search postgresql
sudo dnf install -y postgresql15   # 検索結果に合わせて名前を変える（例: postgresql16）

# バージョンを確認する
psql --version
```

**なぜ psql を入れるか**: DB に接続して、テーブルを作ったり、中身を確認したりするための基本道具です。アプリの DB と同じ PostgreSQL の系統を使うのが安全です。

## 8. 手順 E：停止・起動・終了の違い（ここが一番の混乱ポイント）

| 操作                  | 何が起きるか             | 料金                                                     | データ                                                   |
| --------------------- | ------------------------ | -------------------------------------------------------- | -------------------------------------------------------- |
| **Stop（停止）**      | 電源を切る               | インスタンス料金は止まる。**EBS のディスク料金は続く**   | EBS のデータは残る。**インスタンスストアは消える**       |
| **Start（起動）**     | 再び電源を入れる         | インスタンス料金が再び発生                               | EBS のデータは残る。**パブリック IP が変わる**ことがある |
| **Terminate（終了）** | サーバーを完全に削除する | 停止。ディスク（デフォルトでは終了と同時に削除）も消える | **消える。元に戻せない**                                 |

**学習のルール**

- 使わない時間は **Stop** する（料金を抑える）。
- 不要になったら **Terminate** する（ディスク料金も止まる）。
- **Terminate の前に、残したいデータを S3 などに移す。**

## 9. 運用

### 9.1 毎月やること

| 作業                                                  | 理由                                     |
| ----------------------------------------------------- | ---------------------------------------- |
| `sudo dnf update -y` で OS を更新する                 | セキュリティの穴を埋めるため             |
| 使っていないインスタンスを Stop または Terminate する | 料金を抑えるため                         |
| タグの確認（`Owner`・`Env`）                          | 誰の何のサーバーか分からなくならないため |

### 9.2 監視（CloudWatch）

- インスタンスの画面 → **Monitoring** タブで、CPU の使用率を確認する。
- **アラーム**の例: CPU 使用率が 80% を 15 分以上続いたら通知する（CloudWatch は無料枠の対象に含まれる）。
- **なぜ**: 処理が止まった、暴走している、などの異常に早く気づくため。

### 9.3 バックアップ（EBS のスナップショット）

- EC2 → Volumes → 対象のボリューム → **Create snapshot**。
- **なぜ**: OS や設定を壊した時に、スナップショットから復元できるようにするため。
- スナップショットにも、保存料金がかかる。**不要になったら消す。**

### 9.4 「踏み台」の使い方のルール

- 踏み台に入るのは、**DB の確認や作業をするときだけ**。
- 作業が終わったら、`exit` でセッションを閉じる。
- 踏み台に、アプリの秘密の値（パスワードなど）をファイルで置かない。作業が必要なときだけ、その場で入力する。

## 10. 後片付け（学習後）

1. 作業が終わったら、EC2 を **Terminate** する（必要なら前もってスナップショットを作る）。
2. ボリュームが残っていないか確認する（**EC2 → Volumes**）。残っていたら削除する。
3. 使っていない Elastic IP があれば、解放する（料金の対象になることがある）。
4. IAM のロールとインスタンスプロファイルは、残しても料金はかからない。必要なければ消す。

## 11. 要確認

1. 簡易版で、対象のインスタンスタイプ（t3.micro / t4g.micro）が起動できるか（無料枠の対象か）
2. Amazon Linux 2023 の PostgreSQL パッケージの名前（`dnf search postgresql` で確認）
3. パブリック IPv4 アドレスの料金（EC2 の料金ページで確認）
